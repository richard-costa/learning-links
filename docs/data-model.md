# Data model

Learning Links records **encounters**, not prerequisite/support relationships.

## Semantics

An encounter answers one sentence:

> While studying **context**, I flagged **topic**.

The optional reason records intent rather than claiming an objective dependency:

- `need` — this felt like a gap worth learning;
- `revisit` — I know some of it but want a review;
- `curious` — an interesting tangent or connection.

The optional note stores why it surfaced.

## PostgreSQL

Every persisted workspace record belongs to a user. Topic names are unique only within one user's workspace, so two users can independently have a topic named `Differential Equations`.

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email TEXT NOT NULL,
    password_hash TEXT NOT NULL,
    active BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE topics (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name TEXT NOT NULL,
    url TEXT,
    status TEXT NOT NULL
);

CREATE TABLE encounters (
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    context_topic_id BIGINT NOT NULL,
    topic_id BIGINT NOT NULL,
    reason TEXT NOT NULL,
    note TEXT NOT NULL DEFAULT '',
    PRIMARY KEY(context_topic_id, topic_id),
    FOREIGN KEY(user_id, context_topic_id)
        REFERENCES topics(user_id, id) ON DELETE CASCADE,
    FOREIGN KEY(user_id, topic_id)
        REFERENCES topics(user_id, id) ON DELETE CASCADE,
    CHECK(context_topic_id <> topic_id)
);
```

The composite foreign keys enforce that both sides of an encounter belong to the same user. Application queries also include `user_id`, so one authenticated workspace cannot read, update, reset, or connect another user's topics.

A topic can therefore be queried in two directions without inventing inverse prose:

- `encounters.topic_id = topic.id` → **Came up in**;
- `encounters.context_topic_id = topic.id` → **Led me to**.

Discovery is primarily `COUNT(encounters.context_topic_id) GROUP BY encounters.topic_id` within one user's workspace: how many distinct contexts caused a topic to resurface.

## Existing database migration

When an older database has topics without `user_id`, startup migrates them in place. If exactly one active user exists, that user becomes the owner of the existing workspace. If multiple active users exist, set `LEARNING_LINKS_MIGRATION_USER` to the email of the existing user who should own that data; startup refuses to guess otherwise.

## API representation

```json
{
  "topics": [
    { "id": "1", "name": "Classical Mechanics", "status": "learning", "url": "" },
    { "id": "2", "name": "Differential Equations", "status": "planned", "url": "" }
  ],
  "encounters": [
    {
      "id": "1--2",
      "context": "1",
      "topic": "2",
      "reason": "need",
      "note": "Harmonic oscillator equations"
    }
  ]
}
```

`user_id` is deliberately not supplied by the browser. The backend derives workspace ownership from the authenticated user and scopes every database operation accordingly.

The frontend and backend use the same domain vocabulary: `topics`, `encounters`, `context`, `topic`, `reason`, and `note`.
